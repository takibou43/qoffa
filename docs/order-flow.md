# تدفّق الطلب — قُفّة

## المسار الطبيعي

```
PENDING            الزبون أنشأ الطلب، بانتظار المحل
   ↓ (المحل)
SHOP_ACCEPTED      المحل قبل
   ↓ (المحل)
PREPARING          جاري التحضير
   ↓ (المحل)
READY_FOR_PICKUP   جاهز — يبدأ البحث عن موصّل تلقائيًا
   ↓ (الموصّل يقبل العرض)
DRIVER_ASSIGNED    تعيين موصّل
   ↓ (الموصّل)
PICKED_UP          استلم من المحل
   ↓ (الموصّل)
OUT_FOR_DELIVERY   في الطريق للزبون
   ↓ (الموصّل)
DELIVERED          تم التسليم ← تُحسب العمولة وأجرة الموصّل
```

## الحالات الاستثنائية

| الحالة | من يسبّبها | نهائية؟ | المخرج |
|---|---|---|---|
| `REJECTED` | المحل قبل بدء التحضير | نعم | سبب الرفض مُلزم |
| `CANCELLED` | الزبون قبل `PREPARING`، أو الإدارة، أو المحل بعد `NO_DRIVER` | نعم | يُسجَّل من ألغى والسبب |
| `NO_DRIVER` | النظام بعد استنفاد العروض | **لا** | يمكن إعادة المطابقة → `READY_FOR_PICKUP` |
| `FAILED_DELIVERY` | الموصّل | **لا** | الإدارة تعيد المحاولة → `OUT_FOR_DELIVERY` |

## قواعد الصلاحية لكل انتقال

المصدر: `backend/src/services/orderStateMachine.ts` — جدول `TRANSITIONS`.

- **الزبون**: الإلغاء فقط من `PENDING` و`SHOP_ACCEPTED`. لا يستطيع تسليم طلبه بنفسه.
- **المحل**: القبول والرفض قبل التحضير، ثم `PREPARING` و`READY_FOR_PICKUP`. لا يستطيع تنفيذ خطوات الموصّل.
- **الموصّل**: `PICKED_UP`، `OUT_FOR_DELIVERY`، `DELIVERED`، `FAILED_DELIVERY`، والانسحاب → `READY_FOR_PICKUP`.
- **الإدارة**: تدخّل استثنائي — يمر من نفس آلة الحالات ويُسجَّل في `AdminAuditLog`.

أي انتقال غير مذكور في الجدول → **409**. انتقال صحيح من جهة غير مخوّلة → **403**.

## مطابقة الموصّل

عند `READY_FOR_PICKUP`:

1. اختيار الموصّلين المؤهلين: معتمد · متاح · **بلا طلب جارٍ** · حسابه فعّال · موقعه معروف · داخل `SEARCH_RADIUS_KM` · لم يُعرض عليه هذا الطلب سابقًا.
2. ترتيبهم بالأقرب إلى المحل، وإرسال **عرض حصري واحد** بمهلة `DRIVER_OFFER_TIMEOUT_SECONDS`.
3. الرفض أو انتهاء المهلة → العرض التالي. لا يُفتح الطلب لكل الموصّلين في آن واحد.
4. بعد `MAX_DRIVER_OFFERS` أو انعدام المؤهلين → `NO_DRIVER` (والطلب **لا يُلغى**).
5. مؤقّت في الخادم ينهي العروض المنتهية ويستأنف المطابقة دوريًا.

### الحماية من السباق

قبول العرض يتم داخل **معاملة واحدة** بقفلين شرطيين، بلا `SELECT` ثم `UPDATE` منفصلين:

```
1) قفل الموصّل:
   UPDATE DriverProfile SET currentOrderId = :order
   WHERE id = :driver AND currentOrderId IS NULL
     AND status = 'APPROVED' AND isAvailable = true
   → count = 0 ⇒ رفض

2) قفل الطلب (داخل transitionOrder):
   UPDATE "Order" SET status = 'DRIVER_ASSIGNED', driverId = :driver
   WHERE id = :order AND status = 'READY_FOR_PICKUP' AND driverId IS NULL
   → count = 0 ⇒ رفض وتُرجَع المعاملة كاملة
```

عند تزامن موصّلين اثنين، يُسلسِل PostgreSQL التحديثين على الصف نفسه: الثاني يعيد `count = 0` فيفشل بـ**409**.
مُغطّى باختبارات فعلية: موصّلان، خمسة موصّلين متزامنين، وسباق عبر HTTP API.

## بعد التسليم

- تُحسب عمولة المنصة من قيمة المنتجات (`commissionBps` الخاص بالمحل).
- تُحسب أجرة الموصّل من رسوم التوصيل (`DRIVER_FEE_SHARE_BPS`).
- تُسجَّل حركات في `WalletTransaction` ويُحدَّث رصيد `Wallet` للمحل والموصّل.
- يُحرَّر الموصّل (`currentOrderId = null`) وتُلغى العروض المعلّقة.
- يصبح بإمكان الزبون تقييم المحل والموصّل — **مرة واحدة لكل هدف** (مضمون بقيد فريد في قاعدة البيانات).
